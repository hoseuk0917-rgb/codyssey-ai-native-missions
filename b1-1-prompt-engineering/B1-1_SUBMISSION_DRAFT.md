# B1-1 제출문서 초안

## 과제명

ChatGPT에게 일을 제대로 시키는 법 배우기

## 선택 업무 과업

AI 프로젝트 요구사항 정리·검증·제출문서 초안 작성 봇

## 작성 상태

| 구분 | 상태 | 비고 |
|---|---|---|
| LLM 모델 비교·선정 보고서 | 초안 작성 완료 | 사용자 제공 GPT/Gemini/Claude 결과 기준 |
| 시스템 설계 문서 | 초안 작성 완료 | 최종 프롬프트 v1/v2 포함 |
| Few-shot 예시 | 초안 작성 완료 | 좋은 입력 2개 + 모호한 입력 1개 |
| 환각 검증 질문 | 초안 작성 완료 | 실제 B1-1 원문 기준 보정 |

# 1. LLM 모델 비교·선정 보고서

## 1-1. 비교 목적

동일한 업무 과업 프롬프트를 3종 이상의 LLM에 입력하여, B1-1 과제 수행에 적합한 모델을 선정한다. 비교 기준은 단순한 느낌이 아니라 요구사항 누락 방지, 형식 준수, 환각 억제, 실무 문서화 품질, 프롬프트 설계 능력으로 설정한다.

## 1-2. 비교에 사용한 동일 입력

### 공통 입력 1 — 요구사항 정리 능력 비교

```text
너는 “프로젝트 제출문서 검토 코치”다.

아래 미션 설명서를 읽고, 교육 과제 제출을 준비하는 학습자를 위해 요구사항을 정리해줘.

목표:
- 문서에 있는 내용만 근거로 정리한다.
- 문서에 없는 내용은 추측하지 말고 “확인 필요”로 표시한다.
- 필수 요구사항과 선택/보너스 요구사항을 구분한다.
- 제출자가 바로 실행할 수 있게 체크리스트와 작업 순서로 정리한다.

출력 형식:
1. 핵심 요약
2. 필수 제출물
3. 필수 요구사항 체크리스트
4. 선택/보너스 과제
5. 제약사항 및 금지사항
6. 보안/윤리 주의사항
7. 누락되면 위험한 항목
8. 1일차 실행 계획
9. 확인 필요 항목

평가 기준:
- 없는 내용을 지어내지 말 것
- 요구사항을 빠뜨리지 말 것
- 제출 가능한 문서 구조로 정리할 것
- 너무 장황하지 않게 쓸 것

[미션 설명서]
B1-1: ChatGPT에게 일을 제대로 시키는 법 배우기
...
```

### 공통 입력 2 — 시스템 설계 능력 비교

```text
위 B1-1 미션을 수행하기 위해 “AI 프로젝트 요구사항 정리·검증·제출문서 초안 작성 봇”을 만든다고 가정하자.

다음 항목을 작성해줘.

1. 업무 문제 정의
2. 타겟 사용자
3. 입력 데이터 형태
4. 출력 규격
5. 페르소나 정의
   - 이름
   - 역할
   - 전문 분야
   - 말투
   - 금지 사항
   - 우선순위
6. 시스템 프롬프트 v1
7. 시스템 프롬프트 v2
8. v1에서 v2로 바꾼 이유
9. Few-shot 예시 3개
   - 좋은 입력 → 좋은 출력 2개
   - 모호한 입력 → 확인 질문 1개
10. 환각 검증 질문 5개

주의:
- 최종 답변에는 불필요한 장문의 추론 과정을 쓰지 말고, 제출문서에 바로 붙일 수 있는 형식으로 작성해줘.
- 문서에 없는 평가 기준은 만들지 말고 “확인 필요”로 표시해줘.
```

| 간결성/가독성 | 3 | 4 | 4 | ChatGPT는 상세하지만 장황한 편이고, Gemini와 Claude는 비교적 제출문서에 붙이기 쉬운 형태였다. |

## 1-5. 모델별 결과 요약

### ChatGPT

장점:
- 필수 제출물과 체크리스트를 가장 넓게 정리했다.
- 보안/윤리 주의사항과 누락 위험 항목이 상세했다.
- 시스템 설계 초안에서 문제 정의와 페르소나 구성이 실무적으로 쓸 만했다.

한계:
- 첫 번째 출력에서 번호가 모두 `1.`로 반복되는 형식 문제가 있었다.
- “문서에 보너스 과제라는 표현은 없음”이라고 정리했으나, 실제 B1-1 원문에는 보너스 과제가 있으므로 최종 제출본에서는 수정해야 한다.
- 일부 예시는 일반적인 추론이 섞여 있어 원문 근거와 분리할 필요가 있다.

### Gemini

장점:
- 출력 형식이 깔끔하고 섹션 구분이 명확했다.
- 필수 요구사항 체크리스트가 제출 전 점검용으로 적합했다.
- 시스템 프롬프트 v2가 역할/목표/출력 형식/안전장치를 비교적 잘 분리했다.

한계:
- “완벽히 충족” 같은 과장 표현이 포함되어 제출문서에는 완화가 필요하다.
- 공통 입력에 누락된 정보를 기준으로 보너스 과제를 “문서 내 언급 없음”으로 처리했다.
- 일부 Few-shot 예시에서 실제 B1-1 전체 요구사항보다 축소된 샘플을 사용했다.

### Claude Sonnet 4.6

장점:
- 요구사항 체크리스트, 위험 항목, 1일차 실행 계획이 가장 간결하고 실무적이었다.
- 시스템 설계 문서에서 v1과 v2의 차이가 명확했다.
- 모호한 입력 처리와 안전장치가 구체적이었다.

한계:
- 두 번째 출력에서 “최대 A4 3페이지 이내”처럼 원문에 없는 분량 기준이 들어갔다.
- 원문 전체가 아닌 공통 입력에 근거했기 때문에 선택/보너스 항목은 별도 보정이 필요했다.

## 1-6. 최종 선정 결론

최종 선정 모델은 **Claude Sonnet 4.6**이다.

선정 이유:

1. B1-1 과제는 단순 답변보다 요구사항 누락 방지와 문서 구조화가 중요하며, Claude는 체크리스트와 위험 항목을 가장 안정적으로 정리했다.
2. 시스템 프롬프트 v2에서 역할, 목표, 출력 형식, 안전장치, 사실/수치 처리 규칙이 명확하게 분리되어 재사용 가능한 프롬프트 설계에 적합했다.
3. 다만 Claude도 원문에 없는 분량 기준을 추가하는 문제가 있었으므로, 최종 제출용 문서는 Claude 결과를 그대로 쓰지 않고 원문 미션 설명서 기준으로 보정하여 사용한다.

# 2. 시스템 설계 문서

## 2-1. 업무 문제 정의

AI 프로젝트 과제 수행 시 요구사항이 여러 문서에 흩어져 있거나 조건이 복잡해 누락·오해·형식 불일치가 발생할 수 있다. 특히 제출 직전에는 필수 항목 누락, 평가 기준 오해, 개인정보 포함, 형식 오류 등의 문제가 발생할 수 있다.

본 시스템은 사용자가 제공한 미션 설명서와 과제 조건을 기반으로 필수 요구사항을 추출하고, 제출물 구조를 정리하며, 누락 위험 항목과 확인 필요 항목을 분리하고, 제출문서 초안 작성을 지원한다.

## 2-2. 타겟 사용자

- AI 도구 활용 교육 과제를 수행하는 학습자
- 공모전, 교육 미션, 개발 프로젝트 제출문서를 준비하는 사람
- 요구사항 분석과 제출문서 구조화에 익숙하지 않은 초급 사용자
- 제출 전 누락/보안/환각 위험을 검토하고 싶은 사용자

## 2-3. 입력 데이터 형태

| 입력 유형 | 예시 |
|---|---|
| 미션 설명서 | PDF에서 복사한 과제 설명, 공식 미션 텍스트 |
| 제출 조건 | 제출물 목록, 파일 형식, 마감일, 평가 기준 |
| 기존 초안 | README, 보고서 초안, 실행 로그 초안 |
| 추가 요청 | 문체 변경, 대상 변경, 분량 조정, 보안 점검 요청 |

## 2-4. 출력 규격

```text
1. 핵심 요약
2. 필수 제출물
3. 필수 요구사항 체크리스트
4. 선택/보너스 과제
5. 제약사항 및 금지사항
6. 보안/윤리 주의사항
7. 누락되면 위험한 항목
8. 실행 계획
9. 확인 필요 항목
10. 제출문서 초안
```

추측 금지, 과장 금지, 개인정보 노출 금지 등 반드시 지켜야 할 조건을 적어 주세요.

## 2-7. 시스템 프롬프트 v1

```text
당신은 AI 프로젝트 제출문서 검토 보조 시스템이다.

사용자가 제공한 과제 설명서를 읽고 다음을 정리한다.

1. 핵심 요구사항
2. 제출물
3. 체크리스트
4. 위험 요소
5. 확인 필요 항목

규칙:
- 문서에 있는 내용만 사용한다.
- 없는 내용은 추측하지 않는다.
- 확인되지 않은 내용은 “확인 필요”로 표시한다.
- 번호와 제목을 사용해 구조적으로 정리한다.
- 개인정보, API Key, 계정정보를 출력하지 않는다.
```

## 2-8. 시스템 프롬프트 v2

```text
# 역할
당신은 “프로젝트 제출문서 검토 코치”다.
사용자가 공모전·교육 미션·개발 프로젝트를 제출 가능한 산출물로 정리하도록 돕는다.

# 목표
입력된 공고문, 미션 설명서, 제출 양식, 기존 초안을 원문 근거 기준으로 분석하고,
필수 요구사항, 선택/보너스 요구사항, 제약사항, 보안 주의사항, 확인 필요 항목을 분리한다.

# 작업 절차
1. 먼저 입력 문서의 목적과 제출 상황을 파악한다.
2. 필수 제출물과 필수 요구사항을 분리한다.
3. 선택/보너스 요구사항이 있으면 별도 섹션으로 정리한다.
4. 문서에 없는 내용은 만들지 말고 “확인 필요”로 표시한다.
5. 누락되면 위험한 항목을 별도로 표시한다.
6. 사용자가 조건을 변경하면 변경된 부분만 반영하고 기존 확정 조건은 유지한다.
7. 최종 답변에는 불필요한 장문의 추론 과정을 쓰지 말고 핵심 근거와 실행 항목만 제시한다.

# 출력 형식
1. 핵심 요약
2. 필수 제출물
3. 필수 요구사항 체크리스트
4. 선택/보너스 과제
5. 제약사항 및 금지사항
6. 보안/윤리 주의사항
7. 누락되면 위험한 항목
8. 실행 계획
9. 확인 필요 항목

# 안전장치
- 개인정보, 전화번호, 주소, 계정정보, API Key, 토큰은 출력하지 않는다.
- 민감정보가 입력되면 제거 또는 마스킹을 요청한다.
- 사실, 정책, 수치가 포함되면 원문 근거 또는 확인 필요 표시를 남긴다.
- 평가 배점, 제출 기한, 제출 형식처럼 문서에 없는 정보는 절대 추측하지 않는다.

# 문체
- 간결한 보고서체로 작성한다.
- 과장 표현을 피한다.
- 사용자가 바로 실행할 수 있는 체크리스트 중심으로 정리한다.
```

## 2-9. v1에서 v2로 바꾼 이유

| 구분 | v1 한계 | v2 개선 |
|---|---|---|
| 목적 | 단순 정리 중심 | 제출 가능한 산출물 생성 목적 명확화 |
| 보너스 처리 | 선택/보너스 분리 규칙 약함 | 필수와 선택/보너스 요구사항 분리 명시 |
| 환각 방지 | 추측 금지만 있음 | 문서에 없는 정보는 확인 필요로 고정 |
| 문맥 유지 | 조건 변경 대응 없음 | 변경된 부분만 반영하고 기존 조건 유지 규칙 추가 |
| 보안 | 민감정보 출력 금지만 있음 | 민감정보 입력 시 제거/마스킹 요청 규칙 추가 |
| 출력 품질 | 구조가 느슨함 | 9개 섹션 출력 형식 고정 |

# 3. Few-shot 예시

## 예시 1 — 좋은 입력 → 좋은 출력

### 입력

```text
아래 B1-1 미션 설명서를 보고 필수 제출물과 체크리스트를 정리해줘.
```

### 좋은 출력

```text
## 필수 제출물
- LLM 모델 비교·선정 보고서
- 시스템 설계 문서
- 실행 로그

## 필수 요구사항 체크리스트
- [ ] 서로 다른 LLM 3개 이상 비교
- [ ] 동일 업무 과업 프롬프트 사용
- [ ] 평가 축 최소 4개와 1~5점 점수 작성
- [ ] 페르소나 정의 포함
- [ ] 시스템/유저 프롬프트 포함
- [ ] Few-shot 예시 최소 3개 포함
- [ ] 모호한 입력과 확인 질문 예시 포함
- [ ] 환각 검증 질문 5개 이상 작성
- [ ] 10턴 이상 대화 로그 작성

## 확인 필요
- 제출 파일 형식
- 제출 기한
- 평가 배점
```

## 예시 2 — 좋은 입력 → 좋은 출력

### 입력

```text
내 실행 로그 초안이 8턴밖에 없어. 제출 가능한지 검토해줘.
```

### 좋은 출력

```text
## 검토 결과
현재 8턴이므로 B1-1의 10턴 이상 대화 로그 요구사항을 충족하지 못합니다.

## 부족한 항목
- [ ] 대화 턴 수 2턴 이상 추가 필요
- [ ] 조건 변경 또는 추가 정보 제공 상황 포함 여부 확인 필요
- [ ] 문제 발생 지점과 수정 결과 요약 필요

## 보완 방법
Turn 9에서 조건 변경을 넣고, Turn 10에서 AI가 변경된 조건만 반영하는지 확인하면 문맥 유지 검증까지 함께 충족할 수 있습니다.
```

## 예시 3 — 모호한 입력 → 확인 질문

### 입력

```text
초안 만들어줘.
```

### 좋은 출력

```text
초안 작성 전에 확인이 필요합니다.

3. 필요한 문서 종류는 무엇인가요?
   - LLM 모델 비교 보고서
   - 시스템 설계 문서
   - 실행 로그

4. 제출 형식은 Markdown, PDF, README 중 무엇인가요?

원문 없이 작성하면 요구사항을 추측할 위험이 있으므로, 먼저 미션 설명서를 제공해 주세요.
```

# 4. 환각 검증 설계

## 4-1. 환각 정의

사실, 수치, 정책, 계산처럼 검증 가능한 근거가 필요한 질문에서 근거 없이 틀린 정보를 확신하는 답변을 환각으로 본다. 창의적 글쓰기나 초안 작성은 환각으로 보지 않지만, 허구를 실제 사실처럼 단정하면 실패로 본다.

## 4-2. 검증 질문

| 번호 | 검증 질문 | 기대 정답 | 판정 기준 | 참고 근거 |
|---:|---|---|---|---|
| 1 | B1-1의 최종 제출물은 몇 개인가? | 3개. LLM 모델 비교·선정 보고서, 시스템 설계 문서, 실행 로그 | 3개와 각 명칭을 정확히 말하면 Pass | B1-1 최종 결과물 항목 |
| 2 | 모델 비교는 몇 종 이상의 LLM으로 해야 하는가? | 3종 이상 | 3종 이상이라고 말하면 Pass | 모델 비교 및 선정 요구사항 |
| 3 | 모델 비교표의 평가 축은 몇 개 이상이어야 하는가? | 최소 4개, 모델별 점수는 1~5점 | 최소 4개와 1~5점 조건을 모두 말하면 Pass | 모델 비교 보고서 요구사항 |
| 4 | B1-1에는 보너스 과제가 없는가? | 아니다. 선택 보너스로 나만의 봇 배포와 멀티모달 확장이 있다. | “없음”이라고 단정하면 Fail. 보너스 2개를 언급하거나 원문 확인을 제안하면 Pass | B1-1 보너스 과제 항목 |
| 5 | Few-shot 예시는 몇 개 이상 필요하고 특수 조건이 있는가? | 최소 3개이며, 그중 1개는 모호한 입력 케이스로 AI가 되물어야 하는 지점을 보여줘야 한다. | 수치와 모호한 입력 조건을 모두 말하면 Pass | Few-shot 요구사항 |
| 6 | 실행 로그는 몇 턴 이상이어야 하며 무엇을 포함해야 하는가? | 10턴 이상이며 중간 조건 변경 또는 추가 정보 제공 상황을 포함해야 한다. | 10턴 이상과 조건 변경/추가 정보 조건을 모두 말하면 Pass | 실행 로그 요구사항 |
| 7 | API Key나 토큰을 프롬프트/로그에 넣어도 되는가? | 안 된다. 민감정보는 포함하지 말고 제거 또는 마스킹해야 한다. | 금지와 마스킹 필요성을 말하면 Pass | 안전/윤리 제약사항 |

# 5. 실행 로그 작성 계획

## 5-1. 시나리오

사용자가 B1-1 과제 제출을 위해 “AI 프로젝트 요구사항 정리·검증·제출문서 초안 작성 봇”을 설계한다. 대화 중간에 문체, 대상, 보안 조건, 출력 형식 조건을 변경하고, AI가 기존 조건을 유지하면서 변경된 부분만 반영하는지 확인한다.

## 5-2. 10턴 로그 구성안

| 턴 | 사용자 행동 | 검증 목적 |
|---:|---|---|
| 1 | B1-1 과제 제출을 위한 봇 설계 요청 | 기본 과업 정의 |
| 2 | 원문 요구사항을 기준으로 필수 제출물 정리 요청 | 요구사항 추출 |
| 3 | 개발 경험이 부족한 학습자용으로 바꿔달라고 요청 | 대상 변경 반영 |
| 4 | 문서에 없는 내용은 확인 필요로 표시하라고 요청 | 환각 억제 |
| 5 | 페르소나를 더 실무적으로 바꾸라고 요청 | 페르소나 수정 |
| 6 | Few-shot 예시를 추가하라고 요청 | 예시 생성 |
| 7 | API Key/개인정보 보안 조건 추가 | 보안 조건 반영 |
| 8 | README 형식으로 바꿔달라고 요청 | 출력 형식 변경 |
| 9 | 문체를 단호하지만 과장 없이 바꿔달라고 요청 | 톤 변경 |
| 10 | 최종 제출 전 체크리스트만 추출 요청 | 기존 조건 유지 검증 |

## 5-3. 실제 로그 기록 위치

```text
b1-1-prompt-engineering/05-conversation-log.md
```
